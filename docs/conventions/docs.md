# 文档

文档一律用中文写，命令、代码里的名字照原样。每份文档只管一件事，读的人不同，写法不同。

## 有哪些

| 文档 | 给谁看 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| `README.md` | 用户 | 一句话说清是什么、亮点、安装、上手、文档目录、许可证 | 开发细节、实现原理 |
| `AGENTS.md` | 代理 | 常用命令、质量关卡、要避开的坑 | 目录和文件介绍 |
| `CLAUDE.md` | Claude Code | 只有一行 `@AGENTS.md` | 别的内容 |
| `CHANGELOG.md` | 用户 | 每个版本新增、变更、修复、移除了什么 | 提交记录的原样搬运 |
| `docs/ARCHITECTURE.md` | 开发者 | 要解决的问题、模块关系、边界、不变量、跨模块的约定 | 每个文件是什么 |
| `docs/PLAN.md` | 自己和代理 | 已定的决定（带日期和原因）、开发步骤、待定 | 实现细节 |
| `docs/development.md` | 开发者 | 环境、`just` 命令、怎么调试、怎么跑某一部分测试 | 架构 |
| `docs/release.md` | 发版的人 | 发版步骤、检查清单、回滚 | 日常开发 |
| `crates/*/README.md` | 开发者 | 这个 crate 管什么、不管什么、不变量 | 逐个函数的说明 |

模板在 [templates/](templates/)。

## README

- 开头一句话说清是什么、给谁用。接着几条亮点，再是安装和最短的上手步骤。
- 也写局限：什么情况下不适合用它。
- 控制在一屏半左右，细节链到 `docs/` 下的文档。
- 截图放 `docs/assets/`，截图里不能出现个人信息（路径、地址、邮箱、用量数字、会话标题）。

## AGENTS.md

每个会话都会读它，要短而准。

- 开头写明按 bedrock 的规范写、建自（或跟到）bedrock 的哪个提交，`just new` 已经写好。
- 写常用命令和质量关卡（提交前必须通过哪些检查）。
- 写“要避开的坑”：熟悉代码的人不看也会做错的事。新加一条要满足[规矩怎么改](README.md#规矩怎么改)里的三条。
- 目录有哪些、文件是干什么的，代理读代码就知道，不写；写了也会很快过时。
- 只管一个 crate 的坑写进那个 crate 的 `README.md`。

## ARCHITECTURE.md

- 先写要解决的问题，再写模块关系（crate 一级，回答“做 X 的代码在哪”）。
- 提名字不放链接（`NoteStore`、`crates/notes-core`），用搜索就能找到，链接会失效。
- 重点写边界和不变量，尤其是“某样东西不存在”的那种（“核心不碰文件系统”“只有 `<项目>-http` 知道 HTTP”），读代码很难看出来。每条写成“**不变量：**……”。
- 不随代码同步改。一年翻两次，把不再成立的删掉、新形成的补上。

## PLAN.md

- “已定”是一张表：编号、问题、结论、日期。结论写做什么和为什么。
- 推翻一个决定时改那一行的结论，在后面注明“（某日改为……，原因……）”，不删掉旧编号。
- “开发步骤”写每一步的内容和验收标准，做完一步标上完成日期和结果要点。
- 还没定的放“待定”，定了就挪进表里。

## CHANGELOG.md

- 最上面是“未发布”，每次合进来就写；发版时改成版本号和日期。
- 每个版本分“新增”“变更”“修复”“移除”，写用户能感觉到的变化。

## 代码注释

- 用中文写，解释为什么这样做、守住了什么约定；代码本身能说清的不重复。
- 公开的类型和函数写一句文档注释，说清它是什么、什么情况下返回错误。
- 跟周围代码的注释密度和写法保持一致。

## 不写进仓库的

- 个人信息：本机路径、IP 地址、邮箱、用量数字、密钥。
- 参考了哪些产品、网站：只写结论，来源记在私有笔记里。
- 文档里只写用到的东西，不写“没有用某某”这类话。
