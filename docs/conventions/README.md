# 规范

用 bedrock 建的项目都按这里的规矩写。每条写了做什么、为什么；骨架（仓库根目录）是这些规矩的参考实现，示例业务是“备忘”，文字和骨架对不上时以骨架为准，并回头改文字。

## 适用范围

- 核心逻辑用 Rust 写，一个仓库放所有端：命令行（也能开服务给别的设备用）、桌面和手机（同一个 Flutter 应用），以及以后的端。
- 只有一个端、一个人一下午能写完的小工具，可以只取需要的部分：目录、检查和文档照旧，分层和操作面按需要简化，但依赖方向不变。

## 规矩怎么改

这些规矩每个会话都会读，要保持少而准。

- 新规矩要同时满足三条：不明显（熟悉代码的人不看也会做错）、反复遇到过、具体到能照做。只是一次的观察，先记在项目的 PLAN 或提交说明里，再遇到再加。
- 写成“要避开的坑”和“必须守住的边界”。模块里有哪些文件、数据怎么流，读代码就知道，而且很快过时，不写进规矩。
- 只管一个项目的写进那个项目的 `AGENTS.md`；只管一个 crate 的写进那个 crate 的 `README.md`。
- 改规矩单独提交，提交说明写清为什么改。规矩和骨架一起改，`just ci` 通过才算改完。
- 项目里发现规矩不合适：先在项目里按实际情况做，再回 bedrock 改规矩，别让项目和规矩长期对不上。
